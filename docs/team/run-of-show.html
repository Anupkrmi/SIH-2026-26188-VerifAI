Know the app — every screen, in plain English

Six screens, always the same left-hand menu. This is what each one is actually for and what's on it — read this once and you'll never be surprised by your own product on stage.

1
Overview
the home screen
What it's for: the first thing anyone sees. It explains the idea before showing any live data — so a judge understands the "why" before watching a demo.
What's on it
  • A short headline statement of what makes this system different
  • The four-step "Trust Ladder" diagram, drawn as a connected chain
  • Two buttons to jump straight into the console or start a new check
  • An honesty section — what the demo does and doesn't claim to be
2
Command Center
the control room
What it's for: the operational hub — proof the system is live, plus one-click demo attacks so you can show every kind of forgery without needing real fake documents on hand.
What's on it
  • Four live status readouts (are the AI models loaded, is the signing certificate ready, is the logbook intact, how many cases so far)
  • Six scenario cards — a genuine document plus five different forgery attempts, each one real and runnable with a click
  • A table of the most recent cases actually run this session
  • The screen says it plainly: "six controlled experiments, not six travellers" — and that the test documents are synthetic while the pipeline processing them is the real one. If a judge asks whether these are real cases, the answer is already on screen.
3
New Screening
the intake desk
What it's for: where you'd bring your own document instead of a canned demo attack — either our demo passport template, or any real document you want to test.
What's on it
  • A toggle between "Demo Document" (our fictional passport) and "Real Document" (any upload)
  • An upload box for the document, and a live camera / photo upload for the person's face
  • A "Screen this document" button that runs the full check and takes you to the result
  • On a real document the result shows two columns — "What we established" beside "What we could not establish". A score of 0 reads "No adverse signals", never "genuine": we can say nothing counted against the document, but not that it was legitimately issued. If a judge asks why it doesn't just say "clean", that is the answer, and it's a strong one.
4
Case File
the verdict page
What it's for: the single most important screen — the full result of one check, with every reason laid out, not just a pass/fail badge.
What's on it
  • The verdict at the top — risk score, band, and which check actually decided it
  • The document image itself, with any suspicious regions boxed
  • All four checks shown as a chain, marking exactly which one "decided here"
  • Each check shows two separate lines — "Checks:" (the question that layer always asks, same every time) and "This case:" (what it actually found here). This is worth pointing out: most tools blur those together, which is how "here's what we look for" gets misread as "here's what we found."
  • Specific findings — e.g. "printed date and machine-readable date don't match" — with the actual mismatched values shown
  • Technical wording is kept but tucked behind a "Technical detail" toggle, so the plain answer comes first
  • A line-by-line technical log of every single check that ran, for anyone who wants to see the full trail
5
Audit Trail
the logbook
What it's for: shows every check ever run this session as a tamper-evident chain, and lets you demonstrate — live — what happens if someone tries to edit a past record.
What's on it
  • A scrolling list of every past case, each with its own cryptographic fingerprint
  • A live "is the chain intact?" indicator
  • Two demo buttons: hand-edit a past record, then re-check the chain and watch it catch the edit
  • A "what this proves" box stating both halves honestly — it catches edits to stored records, and it does not prove any document is authentic. Volunteer this; don't wait to be asked.
6
System Status
the engine room
What it's for: proof, for a technical judge, that nothing is faked or hardcoded — every number here is read live off the running machine.
What's on it
  • Four engine readouts — Biometric engine, Cryptographic engine, Ledger chain, Test suite — each READY/INTACT or not
  • Real file sizes of the AI models actually loaded
  • The demo signing certificate's real fingerprint
  • The live rule weights and risk bands, read straight from the config file
  • The real, current count of automated tests, collected on the spot

The live run-through

Follow this path in order. It's built to land the idea first, prove the app is real second, and end on the strongest moment it has.

If something breaks live

Stay calm — here's exactly what to do:
  • A card doesn't respond to a click: click once more, cleanly. Never double-click rapidly.
  • The live site is slow or down: switch to the localhost backup, say so plainly, keep going.
  • Asked something you're not sure of: hand off by name to the teammate who owns that topic, rather than guessing.
  • Asked to show something not built (offline mode, extra language support, etc.): say "that's on our roadmap, not in the current build" — never imply it exists.
"Our AI can raise a hand and ask a human to look closer. It can never, by itself, get a document rejected."
— land it in the first 30 seconds, echo it in the last 30
